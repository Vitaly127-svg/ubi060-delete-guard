# Проверка после развёртывания

Команды для проверки готовности ресурсов и выполнения HTTP-сценария на развёрнутом кластере.

```bash
kubectl get pods -n pattern -o wide
kubectl get pods -n data -o wide
kubectl get networkpolicy -n data
kubectl -n pattern logs job/bootstrap
python scripts/demo.py --base "https://$(minikube ip):30443" \
  --credentials .local/cluster/credentials.json --ca .local/tls.crt
kubectl -n pattern logs deployment/audit-service --tail=30
```

После создания тестового набора отправьте два одинаковых DELETE с одним Idempotency-Key: результат и срок карантина должны совпасть. Сбой RabbitMQ должен оставлять события в outbox. После восстановления брокера проверьте появление записей в журнале без дубликатов event_id. Карантин должен сохраняться после перезапуска quarantine-service. Сбой после перехода в PURGING должен завершаться повтором DELETE, а не восстановлением в ACTIVE.

Для сетевой проверки нужен отдельный диагностический pod без меток доверенных приложений. Его попытки соединиться с Cassandra:9042 и delete-guard:8002 должны завершаться по тайм-ауту. При этом разрешённый data-api должен читать данные. Проверка CQL-привилегий выполняется отдельно: учётная запись reader должна получать отказ на DELETE и INSERT. NetworkPolicy сама не различает CQL SELECT и DELETE.

При RF=1 нельзя делать вывод об устойчивости к потере одной реплики Cassandra. Для RF=3 нужен заново подготовленный стенд: три pod, keyspace RF=3, разрешённый межузловой трафик и соответствующий бюджет памяти. При недоступной реплике запрос с ALL должен отложить удаление, а не снизить уровень согласованности.

Нагрузочные измерения, параметры k6, задержки и пропускная способность требуют отдельного эксперимента и в текущем отчёте не заявляются.
