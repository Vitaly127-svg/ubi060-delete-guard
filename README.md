# Контролируемое удаление данных при угрозе УБИ.060

Реализация паттерна для курсовой работы. Система проверяет подписанную политику хранения, минимальный срок, общий счётчик запросов, зависимости и доступность данных перед удалением. Разрешённое удаление сначала переводит набор в карантин. До окончательного удаления владелец может восстановить данные.

В репозитории находятся исходный код пяти Python-сервисов, конфигурация шлюза NGINX, Dockerfile, десять файлов манифестов Kubernetes, сценарии развёртывания и демонстрации, тесты и GitHub Actions. Разделы 3.1 и 3.2 курсовой описывают эти файлы.

## Быстрый запуск без Kubernetes

Нужен Python 3.12. В Windows команда Python может называться `py -3.12`.

```bash
git clone https://github.com/Vitaly127-svg/ubi060-delete-guard.git
cd ubi060-delete-guard
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell вместо предыдущей строки:
# .venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/run_local.py --smoke
```

Последняя команда запускает пять настоящих HTTP-процессов на `127.0.0.1:8000–8004`, проверяет сценарий и завершает процессы. Итог записывается в `artifacts/local-smoke.json`. Проверяются ответы 202, 403, 409, скрытие карантина, восстановление, окончательное удаление и целостность журнала. В этом режиме каталог, данные и перенос outbox работают локально через SQLite: результат не доказывает работу Cassandra, RabbitMQ, NetworkPolicy или кластера Kubernetes.

Для ручного просмотра выполните `python scripts/run_local.py`, оставьте терминал открытым, а в другом запустите `python scripts/demo.py --direct`. Swagger доступен, например, по `http://127.0.0.1:8002/docs`. Пароли создаются случайно и сохраняются в `.local/credentials.json`. В новых демонстрациях используйте новые наборы и ключи запросов; удалённый `purge-demo` автоматически не восстанавливается. Для полностью нового локального стенда используйте новую копию проекта без каталога `.local`.

## Развёртывание на Ubuntu и Minikube

Нужны Docker, kubectl, Minikube, Python 3.12 и свободные ресурсы: ориентировочно 4 CPU, 8 ГБ RAM и 10 ГБ диска. Эти значения являются требованиями стенда, а не измеренным результатом нагрузочного теста.

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements-dev.txt
minikube start --driver=docker --cni=calico --cpus=4 --memory=6144
bash scripts/deploy.sh
kubectl get pods -n pattern
kubectl get pods -n data
kubectl get pods -n monitoring
```

Скрипт собирает образ внутри Minikube, создаёт пространства имён, случайные Secret и сертификат для текущего IP, применяет сетевые политики, запускает инфраструктуру, ждёт bootstrap Job и готовности сервисов. Секреты не входят в YAML из Git. При повторном запуске сохраняйте `.local/cluster`: пароли должны соответствовать уже созданным PVC. Применение YAML само по себе не означает успешный запуск — проверяются `rollout status` и завершение Job.

Кластерный профиль содержит один узел Cassandra с RF=1; запросы выполняются с `ConsistencyLevel.ALL`. Это обеспечивает требование ответов всех реплик, заданных текущим RF, но при RF=1 не проверяет отказоустойчивость распределённого хранилища. Профиль с тремя репликами требует отдельных ресурсов, начальной настройки RF=3 и проверки отказов перед выводами о репликации. Работа в Minikube не является производственным развёртыванием.

Для демонстрации через защищённый вход:

```bash
python scripts/demo.py --base "https://$(minikube ip):30443" \
  --credentials .local/cluster/credentials.json --ca .local/tls.crt
```

На некоторых драйверах Minikube IP недоступен с хоста. В отдельном терминале можно выполнить `kubectl -n pattern port-forward service/nginx-gateway 30443:8443` и использовать `--base https://127.0.0.1:30443`. Демо сохраняет `artifacts/demo.json`. Образцы наборов имеют искусственную дату создания 31 день назад; в локальном режиме карантин составляет 8 секунд, в кластере — 60 секунд. Это параметры воспроизводимого примера, а не нормативные сроки.

Панель мониторинга открывается после `kubectl -n monitoring port-forward service/grafana 3000:3000` по `http://127.0.0.1:3000`. Логин `admin`, пароль находится в `.local/cluster/material.json`, поле `grafana`. Grafana доступна через локальный туннель администратора. Для публикации вне стенда нужны отдельные TLS и управление доступом.

## Микросервисы и API

| Компонент | Порт | Основные операции |
|---|---:|---|
| nginx-gateway | 8443 / NodePort 30443 | TLS, auth_request, маршрутизация, лимит запросов |
| auth-service | 8001 | `POST /token`, `GET /verify` |
| delete-guard | 8002 | `POST /catalog`, `PUT /policies/{id}`, `POST /dependencies`, `DELETE /deletions/{id}` |
| quarantine-service | 8003 | `GET /quarantine`, `POST /quarantine/{id}/restore`, фоновое удаление |
| audit-service | 8004 | `GET /audit`, `/audit/verify`, `/notifications`, потребитель RabbitMQ |
| data-api | 8000 | `GET /datasets/{id}`, `POST /datasets` через доверенный сервис записи |

У Python-сервисов есть `/healthz`, `/readyz`, `/metrics` и OpenAPI `/docs`. Внешний шлюз не публикует служебные метрики и Swagger внутренних сервисов: они доступны администраторам через port-forward. Data-api имеет только SELECT в Cassandra, поэтому не может обойти контроль удаления с помощью разрешённого CQL-соединения. Загрузку он передаёт delete-guard с исходным JWT; права проверяются повторно.

Подписанные эталоны привязаны к `dataset_id` и версии. Для новой политики необходима RSA-PSS/SHA-256 подпись. Закрытый ключ эталона доступен bootstrap/администратору, но не delete-guard. JWT использует отдельную пару RSA-ключей и RS256; закрытый ключ JWT установлен только в auth-service. Параметры `iss`, `aud`, `exp` и допустимый алгоритм проверяются явно.

## Алгоритм и границы гарантий

`app/domain.py` содержит операции, используемые API и рабочими процессами. PostgreSQL сериализует изменения каталога через строку `transaction_mutex`. Это простой способ согласовать две реплики guard, счётчики, граф связей и restore/purge; он ограничивает пропускную способность и должен измеряться в главе 4.

`ACTIVE → QUARANTINED → PURGING → PURGED` — путь удаления данных. `DEFERRED` обозначает отложенный запрос: данные остаются читаемыми. Это уточняет служебную пометку из проектной схемы и предотвращает потерю доступности при ответе 409. Решение запроса по-прежнему имеет два исхода: allow (202) и deny (403/409).

Перед ответом 202 состояние и событие outbox записываются одной SQL-транзакцией. Перед CQL DELETE повторяются проверки и отдельно фиксируется PURGING. Сбой после CQL DELETE допускает безопасный повтор; restore и новые зависимости для PURGING запрещены. В Cassandra DELETE создаёт tombstone; освобождение диска происходит позднее при compaction.

RabbitMQ использует durable queue, persistent messages и publisher confirms. Потребитель подтверждает событие после SQL commit и устраняет дубликаты по UUID. Перенос в RabbitMQ допускает повторную доставку; exactly-once транспорт не заявляется. Уведомления доступны в защищённом API `/notifications` и сохраняются в БД. Отправка писем или сообщений внешним адресатам не настроена.

Журнал связан хешами и позволяет обнаруживать изменение отдельных сохранённых записей. Администратор PostgreSQL может пересчитать всю цепочку: абсолютная неизменяемость без внешнего подписанного контрольного хеша не заявляется. Сетевые политики требуют CNI с их поддержкой; штатный профиль использует Calico. Секреты Kubernetes не следует считать зашифрованными только потому, что они представлены объектом Secret.

## Что показывать преподавателю

1. Исходные функции в `app/security.py`, `app/domain.py`, `app/messaging.py`, а также API в `app/api.py`.
2. Локальный запуск и JSON-отчёт: `python scripts/run_local.py --smoke`.
3. Вкладку **Actions**: проверка тестов, соответствия YAML генератору, HTTP-сценария и сборки Docker после загрузки в GitHub.
4. При наличии работающего кластера — `kubectl get pods`, `rollout status`, ответы `scripts/demo.py` и Grafana. Зелёный локальный тест не заменяет этот пункт.

Проверенные локально результаты и ограничения записаны в [docs/verification.md](docs/verification.md). Методика будущей кластерной демонстрации — в [docs/cluster-checks.md](docs/cluster-checks.md).
